# Newsforge 初始化 Playbook（宿主无关契约）

> 这是 Newsforge 初始化的**唯一契约**：问题集、产出物、步骤顺序、完成判据只存这一份。
> 无论执行者是 Muse、Claude Code、Codex 还是 Gemini CLI，都按本文件执行；
> 其他文档（`docs/ONBOARDING.md`、README、`docs/agents/*.md`）只许引用本文件，不许复制问题集或步骤。
>
> 本文件只管**初始化**（从空仓库到首期上线）。每日运行不在本文件范围内。

## 1. 启动指令

用户在仓库根目录打开 agent 会话后，粘贴这一句（仓库地址由用户在粘贴前替换）：

```
我想用 Newsforge 模板建一个每日更新的新闻网站，仓库已经建好了：github.com/<用户名>/<仓库名>。请严格按 playbooks/onboarding.md 的契约帮我初始化：先验证仓库推送权限，再按必答问题集逐组问我，最后按完成判据逐项验收。
```

执行者收到后，先完整读一遍本文件，再从第 6 节的 S0 开始执行，不跳步。

## 2. 执行者能力要求

执行本 playbook 的 agent 必须具备以下能力，缺一不可；缺任何一项时，停下来向用户说明缺什么、给出替代办法（换宿主或用户代操作），不许假装执行过：

- 读写文件：能读仓库内文档、写 `site.json`、`modules/*/module.json`、`public/theme.css` 等产出物
- 对话提问：能逐组向用户提问并等待回答（初始化是多轮对话，不是单次批处理；不要用非交互/批处理模式跑初始化）
- 执行命令：能跑 `git`、`npm`、`node`、`python3`、`curl`
- Git 推送：能把产出物提交并推送到用户仓库（推送通道见 `docs/PUSH-MODES.md`）
- 看图：能打开渲染截图/页面让用户确认，能亲手打开一张配图检查（不是只看 HTTP 状态码）

## 3. 通用规则

- **步骤类型**：每步标注 🤖（你来做，含向用户提问）或 ✋（用户亲手操作，你给到"点哪个按钮"级的指引，等用户说"好了"再继续）。碰到时必须向用户明示当前是哪种。
- **选项铁律**：每次用选项提问，最后一项永远是"以上都不合适，我来填写"。用户选它之后等用户打字，不许追问"具体指什么"，等他说完再继续。不许为了凑选项数删掉这一项。本文件第 4 节每个选项组都已带这一项，执行时不许删改。
- **一次一组**：必答问题集逐组问，一组没答完不开下一组；每组先亮你的推荐，再让用户选。
- **红线**：
  - 用户的 token、密钥绝不进 git、绝不写进任何仓库文件、不在交付汇报里复述；一律存 `~/.config/newsforge/` 下、权限 600
  - 推送上线必须经过用户确认（除非用户明确授权过"自动推送"，见 Q9）
  - 摘要里不许编造：原文没有的写"原文未提"
  - 拿不准就停下来问用户，不许自己猜
- **编辑原则**：只引用 `docs/editorial-principles.md`（6 条预设的 id 与说明都在那里），本文件不复制其内容；用户选中的 id 写入 `site.json → editorial.principles`。
- **宪法生效点**：S3b 填完 §一～§四、§六 后宪法生效，S10 补管线时间后完整；S11 验收时不得有剩余占位符。

## 4. 必答问题集

> 全部必答。"可跳过"只指个别字段（如联系邮箱），组本身不许整组跳过。
> 提问顺序即编号顺序。选项组末尾的"以上都不合适，我来填写"是铁律项，不许删。

### Q2 模块与信源

一个模块 = 首页上的一个板块，独立目录 `modules/<id>/`。

- Q2-1 板块选择：先根据 Q0/Q1 的意图**主动推荐 4–6 个板块**，让用户勾选；不许开放式问"你想要哪些领域"。
  选项（可多选）：（执行者现场推荐的板块列表） / 以上都不合适，我来填写
- Q2-2 每个选中板块的信源从哪来？（逐板块问）
  选项：用你推荐的信源 / 我自己给信源 / 以上都不合适，我来填写
  - 选"推荐" → 查 `docs/recipes.md` 对应领域的推荐信源，列出来让用户勾选（勾选同样保留"以上都不合适，我来填写"末项）
  - 选"自建" → 用户给 RSS 链接或网站列表，执行者逐个验证可达性，不可达的当场说明并请用户换
- Q2-3 每个板块逐个确认三项（填空确认即可）：板块名称、副标题（一句话定位）、排序位置

产出：每个模块一份 `modules/<id>/module.json`（格式照 `modules/cyber/module.json`）。用户模块全部生成后，静默删除示例模块 `modules/cyber/`（不用问）；例外：用户明确说要保留它作正式模块，才留。

### Q4 Telegram 订阅（默认不启用）

- Q4-1 要不要 Telegram 频道订阅推送？
  选项：不要（推荐默认） / 要 / 以上都不合适，我来填写
- 选"要"后，✋ 用户手动三件事（一步步带，不许跳）：
  1. 建频道：Telegram → ✏️ → New Channel → 起名 → 选 Public
  2. 建 Bot：找 @BotFather → `/newbot` → 按提示起名 → 把它给的 token 发给执行者（只发这一次；执行者存 `~/.config/newsforge/telegram-token`，600，绝不进 git）
  3. 把 Bot 设为频道管理员并勾 **Post Messages**（不做这步推不出去）；推荐再置顶一条欢迎消息（介绍频道内容和更新时间）
- Q4-2 每天几点推送？（默认跟网站更新时间走）
  选项：跟更新时间走（推荐） / 我来填写时间
- Q4-3 推送范围？
  选项：全部头条 / 只推标 🔥 的 / 以上都不合适，我来填写

写入位置：`site.json → features.telegram`（含频道名；token 不进 site.json）。

### Q9 推送模式与定时任务

- Q9-1 每日推送用哪种模式？（两种模式的原理与代价见 `docs/PUSH-MODES.md`）
  选项：全自动（推荐，构建好直接推送、上线后汇报；要求 PAT 已配好） / 手动确认（每天先汇报，你说推送才推） / 以上都不合适，我来填写

## 7. 完成判据

以下全部满足才算初始化完成，缺一项就继续做或如实告诉用户缺什么：

1. **site.json 校验通过**：`site.json` 存在且能被 JSON 解析；`site.name`、`site.tagline`、`site.timezone`、`site.language` 非空；字段与 5.2 表一致，未启用的功能开关明确写了 `false` 而不是缺失
2. **模块就位**：每个启用模块都有 `modules/<id>/module.json` 且 `id` 与目录名一致；示例模块已按 Q2 结论删除或保留
3. **probe-sources 跑通**：`npm run probe` 执行成功；每个模块至少 1 个信源可达，死源已与用户确认换源或移除
4. **首期 dry-run 构建成功**：首期 edition 已生成，`npm run render` 渲染成功，用户开着 QA 时 `npm test` 通过；渲染结果已给用户看过并确认
5. **线上验收**：Pages 部署后 curl 首页 HTTP 200、标题是用户的站名、首页内容是首期内容（不是空站）；curl `/feed.xml` 条目数与当期一致；头条配图亲手打开看过至少一张（不只验状态码）；启用 Telegram 时首日头条已推送到频道
6. **secrets 就位**：5.4 清单里本用户需要的密钥都已存进 `~/.config/newsforge/` 且权限 600；`git status` 里没有任何密钥文件待提交
7. **宪法就位**：`constitution.md` 无剩余 `{{...}}` 占位符；§五管线时间已按 S10 结论填好；文件已进 git（`git status` 里无未提交的宪法改动）

## 8. 宿主差异说明

- **Muse（零 API 成本模式）**：定时任务、推送审批等平台能力由宿主提供，S10 直接建任务；推送通道见 `docs/PUSH-MODES.md`。
- **终端 agent CLI（BYOK 模式）**：初始化是一次性交互会话，用用户自己的 API key 或订阅登录执行；成本只有这次会话的 token 量，很小。各家 CLI 的装法、登录与注意事项见 `docs/agents/claude-code.md`、`docs/agents/codex.md`、`docs/agents/gemini-cli.md`。每日运行不在本 playbook 范围：终端 CLI 不能常驻，S10 按 Q9-2 把三条路（GitHub Actions / 换能建定时任务的宿主 / 本机手动）摆给用户选，不许假装建好定时任务。
- 两种宿主执行的是同一份问题集、产出物与判据，不许因宿主不同删减问题组或判据项。

## 9. 失败时如何求助

- **某一步卡住**：停在当前步，如实向用户说明三件事——卡在哪一步、报什么错、你试过什么。不许跳过失败步骤假装完成，不许把半成品当成品交付。
- **信源全灭 / 抓不到内容**：按 S6 的硬门槛处理（换源、放宽口径、减模块），和用户一起调，不许用编造内容凑首期。
- **构建或 QA 失败**：先看 `node pipeline/run.js` 报错定位到具体信源或模块；常见问题查 `docs/SETUP.md` 第 9 节故障排查。修不好就把完整报错原文呈现给用户，请用户决定（换信源 / 先关 QA / 改天再试）。
- **权限与密钥问题**：仓库权限走 `docs/PUSH-MODES.md`；R2 走 `docs/R2-IMAGES.md`；都解决不了时，明确告诉用户需要他亲手完成哪一步，并给出操作路径。
- **超出本 playbook 的需求**（改模板代码、加新功能）：告诉用户这属于初始化之外的改动，问他要不要单独开一个任务处理，不要在初始化里顺手改模板。
