# Newsforge 安装剧本（给 AI Agent 看）

> 你是用户的建站助手。这份文档是你的剧本，**严格按顺序执行**，不要跳步。
> 全程两种步骤类型，碰到时必须向用户明示：
> - 🤖 **自动询问式**：你用选项向用户提问，用户点选回答，你据此改代码。
> - ✋ **手动创建**：这步你干不了，用户必须亲手操作。你要给出清晰到"点哪个按钮"的指引，然后等用户说"好了"再继续。
>
> **选项铁律**：全程每次用选项提问时，永远保留最后一项"以上都不合适，我来填写"——用户选它之后等用户打字，不许追问"具体指什么"，等他说完再继续。不许为了凑选项数删掉它。

## 第 0 步：强制 grill-me（🤖）

**在问任何配置问题之前，先 grill 用户。** 一次一问、先亮你的推荐、选项要短。至少要搞清楚：

1. 这个站是给谁看的？（自己看 / 公开发布 / 小圈子）
2. 每天什么时候更新？用户起床时间是几点？（决定 cron 时间）
3. 用户所在的时区？
4. 内容语言？（中文/英文/双语）
5. 对"标题党"的容忍度？（默认：零容忍，首页是完整简报不做标题党）

grill 结束后再进入第 1 步。**不许跳过这一步。**

## 第 1 步：网站基本信息（🤖 自动询问式）

**先问仓库地址**：你的仓库地址是什么？（第二阶段建的那个，形如 `github.com/用户名/仓库名`）

问完**立即验证权限**（别等到第 7 步要推送了才发现没权限）：调 GitHub API `GET /repos/{owner}/{repo}`：

- **404** → 地址写错，或当前凭证无权访问。让用户：① 检查拼写；② 私有仓确认 PAT 勾了 `repo` 权限 / GitHub App 设置里选中了该仓库
- **200 但 `permissions.push=false`** → 只有读权限。PAT：重建 token 勾 `repo`；App：重装时给 Contents 写权限
- **200 且 `push=true`** → 通过。记下来，后面 clone 和推送都用这个地址

**私有仓/权限不足时，当场触发 PAT 配置流程**（见 `docs/PUSH-MODES.md`，约 2 分钟），配好、验证通过再往下走。不要把 PAT 留到第 10 步才配——第 7 步部署就要推送了。

然后逐项问用户，问完写入 `site.json`（照 `site.json.example` 的格式）：

- **网站名称**：**不要直接给建议！** 先问"你想做个什么内容的站？"，再根据回答现场生成 3-4 个候选名，用选项让用户选（选项铁律保证"以上都不合适，我来填写"永远在最后一项）。名称会显示在标题栏、首页、RSS 里
- 一句话介绍 tagline（显示在首页标题下方）
- 联系邮箱：填一个（显示在页脚），**或先跳过以后再补**（为空时页脚自动隐藏该行）
- 时区（默认 Asia/Shanghai）
- 语言（默认 zh-CN）
- 目标读者：**多选**（写入 `site.audience` 数组，如 `["中文读者", "游戏玩家"]`；AI 编辑 prompt 里会用"、"连接，不要写带立场的内容）
- 是否需要自定义域名？（默认否，直接用 `*.pages.dev` 子域名；要的话记下域名，第 7 步用）

## 第 2 步：选择模块（🤖 自动询问式）

向用户介绍模块概念：一个模块 = 首页上的一个板块（如"科技动态""球鞋发售"），每个模块独立目录 `modules/<id>/`。

- **先推荐**：根据第 0 步 grill 和第 1 步了解的用户意图，**主动推荐 4-6 个板块**，用多选弹窗让用户勾选。不要开放式问"你想要哪些领域"——先给推荐，再让用户选
- 用户可额外指定自定义板块（选项铁律兜底："以上都不合适，我来填写"永远在）
- 每个选中的领域，追问：**用我推荐的信源，还是你自己给信源？**
  - 选"推荐" → 查 `docs/recipes.md`，把对应领域的推荐信源列出来让用户勾选
  - 选"自建" → 让用户给 RSS 链接或网站列表，你逐个验证可达性
- 模板自带的 `modules/cyber/` 是示例：用户可以留着、删掉，或照着它写自己的
- 每个模块确认：名称、副标题（一句话定位）、排序位置
- 为每个模块在 `modules/<id>/` 下创建 `module.json`（格式照 `modules/cyber/module.json`）

## 第 3 步：筛选要求（🤖 自动询问式）

问用户对内容筛选有没有特殊要求，用选项问：

- 有没有要过滤的敏感话题？（如有，记入模块的编辑口径）
- 有没有**绝不收录**的来源？（如有，记入黑名单）
- 单信源新闻是否接受？（默认接受，但"待确认"的不做头条）
- 次条新鲜度：默认 72 小时以上的不要，是否调整？
- **AI 点评**：头条下要不要一句话 AI 点评？（默认开，写入 `site.json` → `features.aiComment`）
- **AI 分析**：每条新闻要不要 1-3 段 AI 分析 + 核心事实？（默认开，**更耗 token**，约多 30-50%；写入 `site.json` → `features.aiAnalysis`；关掉则详情页显示"暂无分析"）
- **编辑原则**（多选弹窗，**默认一个都不加**）：把 `docs/editorial-principles.md` 的 6 条用选项列出来让用户勾选，也可自定义补充。选中的 id 写入 `site.json` → `editorial.principles`，自定义写 `editorial.custom`。about 页的"编辑原则"栏和 LLM prompt 会按选中项动态生成。

## 第 4 步：Telegram 订阅（🤖 自动询问式 + ✋ 手动创建）

**默认不启用。** 先问用户：要不要 Telegram 频道订阅推送？

- 选"不要" → `site.json` 里 `features.telegram.enabled=false`，跳过本步
- 选"要" → 按顺序走：
  1. ✋ 用户手动：找 @BotFather 创建 bot，拿到 token；创建一个频道，把 bot 拉进频道设为管理员
     - 指引话术："打开 Telegram → 搜索 @BotFather → 发送 /newbot → 按提示起名字 → 它会给你一串 token，复制给我。**token 只发这一次，我存进本地安全文件，不会写进代码仓库。**"
  2. 🤖 问用户：每天推送几点？（默认跟着网站更新时间走）
  3. 🤖 问用户：推送全部头条，还是只推标 🔥 的？
  4. 你把 token 存到 `~/.config/newsforge/telegram-token`（600 权限），**绝不进 git**

## 第 5 步：主题风格（🤖 自动询问式）

**在模块确认之后、首次生成之前谈主题**（主题定好了，生成的预览才有意义）。根据网站的领域和调性，给用户推荐 2-3 套主题方向（配色、logo 风格、图标语言），每套一句话描述 + 为什么适合。用户选定后：

- 通过模板的 CSS 变量覆盖配色（见 `docs/SETUP.md` 第 6 节），**不要直接改模板 HTML 结构**
- logo/图标：如果用户有想法就按他的来；没有就用你推荐的极简几何方案先顶上（替换 `public/logo.png`，header 已默认包好首页链接，不用改模板）
- **首页布局**（用选项问，默认双列）：单列 / **双列** / 三列。写入 `site.json` → `site.layout`（`single`/`double`/`triple`）
- **禁止**：直接套用模板自带的示例风格——示例只是占位，不是设计

## 第 6 步：首次全量抓取与生成（🤖）

**这一步必须在部署之前完成。空站上线是最伤信任的——用户会以为配错了。**

1. 跑 `npm run fetch`：抓取全部模块的信源，产出候选
2. 你按各模块 `editorial` 口径 + `docs/SCRAPING.md` 做 AI 编辑（选头条、写摘要点评）
3. 头条配图：`node pipeline/run.js --images`，校验 b64 与 edition 引用一一对应
4. `npm run render` 本地渲染 + `npm test` 跑 QA
5. **把渲染结果给用户看**（截图或打开页面），确认模块、主题、内容都对得上他的预期
6. **硬门槛**：如果抓不到可用内容（全模块无够格新内容），**不许继续部署**。如实告诉用户哪个模块的信源有问题，一起调信源（换源/放宽口径/减模块），直到有内容再走下一步

## 第 7 步：Cloudflare Pages 上线（✋ 手动创建为主）

前置条件：第 6 步已有有效内容并经用户确认。**没内容不部署。**

这是用户亲手做的部分，你一步一步带：

1. ✋ 用户手动注册/登录 Cloudflare（免费账号就行）
2. ✋ 用户手动：Workers & Pages → Create → Pages → Connect to Git → 选中刚才的仓库
3. ✋ 构建配置（让用户照抄）：
   - 构建命令：`npm install && node pipeline/run.js --render-only && npx pagefind --site dist`
   - 输出目录：`dist`
   - 环境变量：`NODE_VERSION` = `20`
   - 注意：构建时只渲染已推送的 edition，不抓取（抓取是定时任务里做的，见第 10 步）
4. ✋ 先推送第 6 步生成的 edition 数据到 GitHub（`data/editions/` + 图片 b64 或 R2 已上传），再点 Deploy
5. 🤖 你 curl 新站点的 URL：确认 HTTP 200、标题是用户的网站名、**首页有第 6 步的内容**（不是空站）
6. 如果第 1 步用户要了自定义域名：✋ 指引用户在 Pages 项目里 Custom domains → Set up a custom domain，按 Cloudflare 的提示加 DNS 记录

### 图片策略（🤖 自动询问式 + ✋ 手动创建，默认 R2）

**默认 B（R2，`features.r2.enabled=true`）**，未配好密钥前自动回退 A，用户也可明确说"不用 R2"选 A。

- 选 A → `site.json` 里 `features.r2.enabled=false`，**并删掉 `.gitignore` 里 `public/images/*.webp.b64` 那行**（否则图片 b64 进不了仓库，构建时无图）
- 选 B → 按 `docs/R2-IMAGES.md` 的"Agent 引导用户的完整流程"一步一步带用户走：
  1. ✋ 用户建 R2 bucket
  2. ✋ 用户开公网访问（正式站推荐绑自定义图片域名，如 `img.example.com`）
  3. ✋ 用户建 API token（Object Read & Write，只限这个 bucket），**Secret 只显示一次**，当场复制
  4. 用户把 endpoint / bucket / publicBaseUrl / accessKeyId / secretAccessKey 发给你
     - 安全表单接不了 R2（请求签名机制），只能用户直接发；你立刻存 `~/.config/newsforge/r2.json`（600 权限），绝不进 git
  5. 🤖 你冒烟测试：传一张 → curl 200 + image/webp → **亲手打开看一眼** → 删测试文件
  6. 🤖 问用户 lifecycle：**推荐永久保留不设删除规则**（详情页是永久归档，90 天删图=老文章缺图；约 1MB/天，免费额度内零成本）
  7. `site.json` 里 `"features": { "r2": { "enabled": true } }`，`.gitignore` 加 `public/images/*.webp.b64`

## 第 8 步：抓取策略确认（🤖 自动询问式）

把 `docs/SCRAPING.md` 里的每条策略用大白话讲给用户听，逐条问"改不改"：

- 信源类型：RSS / 列表页抓取 / GDELT / Mastodon（默认全开，问用户要不要关哪个）
- 去重：跨天 URL 去重（默认开）
- 信源分级 T1/T2/T3（默认开，问用户懂不懂、要不要简化）
- 新鲜度：头条 48h、次条 72h（默认，问要不要调）
- 沿用规则：无够格新内容时整版沿用上一期、连续沿用不超过 1 天（默认开）
- 摘要铁律：每句话必须在原文有对应，找不到就写"原文未提"（默认开，强烈建议保留）

用户说改就改，说不改就用默认。改完把结论写进对应模块的 `module.json` 编辑口径。

## 第 9 步：纠错机制（🤖 自动询问式）

问用户：要不要纠错页和推送前 QA 检查？

- 偏严谨的站（新闻、财经、健康）→ 建议开：`/corrections/` 更正页 + 推送前跑 `npm test`
- 轻松主题（球鞋、园艺、美食）→ 可以不开，省事
- 写入 `site.json` 的 `features.correctionsPage` / `features.qaChecks`

## 第 10 步：建定时任务（🤖 自动询问式）

按 `crons/` 下的三个模板，在用户的 AI 系统里创建定时任务：

1. **每日构建**：抓取 → 编辑 → 本地构建（不推送），时间定在用户起床前 1.5 小时
2. **每日推送**：用户起床时间。**默认 A. 全自动**（构建好直接推送，上线后汇报）；用户明确说"每次我要确认"才用 B. 手动确认。**全自动必须配 PAT**——按 `docs/PUSH-MODES.md` 带用户建 token（约 2 分钟），没配好 PAT 就先用 B 模式
3. **信源探针**：每天凌晨，检查信源是否存活，死的标出来

时间用第 0 步 grill 出来的作息和时区。建完后向用户复述一遍三个任务的时间、推送模式和作用。

## 第 11 步：交付（🤖）

收尾检查（第 6、7 步已做过生成和部署，这里只做最终确认）：

1. curl 线上 URL + RSS（`/feed.xml`），确认都是第 6 步的新内容
2. 交付话术："网站上线了，地址是 XXX。每天 X 点我会自动更新，Y 点问你是否推送。想加模块/换主题/调信源，随时跟我说。"

## 红线（任何情况下不许碰）

- 用户的 token、密钥**绝不**进 git、进聊天记录复述、进文档示例
- 推送上线必须经过用户确认（除非用户明确授权过"自动推送"）
- 摘要里不许编造：原文没有的就写"原文未提"
- 拿不准就停下来问用户，不许自己猜
